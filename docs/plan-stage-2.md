## Принципы этапа 2

1. **Профиль пользователя на сервер не попадает** (ADR-004). Сбор работает только с публичными сведениями о банках.
2. **Браузер не ходит в Supabase.** Чтение только на сервере в загрузчиках `'use cache'`. CSP (`connect-src 'self'`) и бюджет первой загрузки (AC-8) не меняются.
3. **`DataGateway` не меняется.** Supabase — третья реализация рядом с `mock` и `http`. У `DatasetInfo` в шаге 3 добавляется `domains` (ADR-019).
4. **Схемы `@fa/contracts` — единый источник правил** на сборе и на чтении.
5. **Деньги и ставки без float** (ADR-003, ADR-013). Ставки строкой, деньги целыми центами. Метрики банков в контракте `number` — исключение, как и сейчас.
6. **У каждого факта источник** (`Provenance`). Государственные API: `verified`, `by: official_api`. Скрейпинг: `unverified` до проверки человеком, затем `verified`, `by: human`.
7. **Не выдумывать значения** (инвариант 6). Нет проверенного источника — `unverified` и задача человеку.
8. **Фикстуры и мок остаются** для тестов, стенда и локальной разработки.
9. **AC-8 держится на реальных данных.** Каталог на моках — 60 CD. Реальный может быть в разы больше; производительность `/compare` проверяется на реальном объёме (шаг 9).

## Шаг 8. Скрейпинг ставок банков (4–5 недель)

### 8.1 Правила в коде

Только публичные страницы без входа; `robots.txt` перед каждым доменом; не чаще 1 запроса в 5–10 с на домен, ночное окно банка, `If-Modified-Since` и `ETag`; User-Agent с проектом и техническим ящиком; капча или блокировка — остановка и ручной режим; журнал нагрузки в `job_runs`; исключение банка за 24 часа; факты и короткие цитаты, снимки только во внутреннем хранилище.

### 8.2 Реестр

Банки из FDIC `institutions` (адрес сайта уже там) и NCUA. Пилот: 10 онлайн-банков с высокими ставками, затем 50 крупнейших по депозитам, затем кредитные союзы с открытым членством. Перед адаптером проверить, нет ли у банка публичного API ставок с регистрацией по email.

### 8.3 Адаптер

JSON на странице → HTML по селекторам из конфига → Playwright, только если без JavaScript ставок нет. Нормализация в `Product`, тест на снимке, правила допуска вносит человек при первом подключении. Поломка — ничего не публикуется, прошлые данные остаются с пометкой свежести.

### 8.4 Документы банков

PDF по ссылкам со страниц продуктов, хеш, `documents`, текст через pdf.js. Факты — предложение скрипта, подтверждение человеком. Подсветка по символам вместо строки (долг ADR-018).

### 8.5 Пилот

| Неделя | Что |
| --- | --- |
| 1 | правила 8.1 в коде, реестр, каркас адаптера, 3 банка |
| 2 | 10 банков, очередь проверки, публикация в `staging` |
| 3 | документы банков, подсветка по символам |
| 4 | 30–50 банков, мониторинг поломок |
| 5 | замер: время поддержки на банк в неделю, доля поломок, доля ручных проверок; решение о масштабе |

**Результат (S2-M3, около 10–11 недель):** реальные ставки CD и savings у 30–50 банков в `staging`.

## Шаг 9. Переключение и запуск (0,5–1 неделя)

- `NEXT_PUBLIC_DATA_SOURCE=supabase` в `staging`, затем в `prod`.
- `isMock: false` только у реальных доменов. Баннер DEMO снимается, когда все домены на странице реальные.
- **Производительность на реальном объёме:** Lighthouse CI с профилем на реальном каталоге. Если каталог сильно больше 60 строк и медиана ниже 0,85 — решение из шага 0 (пагинация, виртуализация или top-N).
- `/methodology`: реальные источники, частота обновления, метод рынка.
- Пороги свежести (7 / 90 / `asOf` + 120) проверить на реальных данных.
- Юрист (шаг 0). После его «да»: убрать `noindex` и `disallow: /`, добавить `sitemap`, снять `DEMO_PASSWORD`.

**Результат (S2-M4):** публичный запуск на реальных данных.

## Шаг 10. Качество (сквозь все шаги)

- Тестовый набор контракта против `staging` ночью.
- Проверки качества данных ежедневно: устаревшие записи по доменам, банки без продуктов, продукты без документа, задачи в очереди старше 3 дней.
- Lighthouse CI и бюджет первой загрузки не хуже фазы 0.
- e2e AC-4: ни одного запроса браузера к Supabase или источникам данных.
- `e2e-browsers` на `main` и ночью.
