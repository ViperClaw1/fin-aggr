## Принципы

1. **Профиль пользователя на сервер не попадает** (ADR-004). Сбор данных работает только с публичными сведениями о банках, персональных данных в нём нет.
2. **Браузер не ходит в Supabase.** Чтение только на сервере в загрузчиках `'use cache'`. CSP (`connect-src 'self'`) и бюджет первой загрузки (AC-8) не меняются.
3. **`DataGateway` не меняется.** Методы те же. Supabase — третья реализация рядом с `mock` и `http`. `http` остаётся заглушкой `not_implemented`. У `DatasetInfo` в шаге 3 добавляется поле `domains` (ADR-019): это расширение схемы, не новый метод.
4. **Схемы `@fa/contracts` — единый источник правил.** Каждая запись проходит их и на сборе, и на чтении.
5. **Деньги и ставки без float** (ADR-003, ADR-013). Ставки строкой (`Rate`), деньги целыми центами. Метрики банков, которые в контракте `number` (проценты и доли для показа), — единственное исключение, как и сейчас.
6. **У каждого факта источник** (`Provenance`): `sourceUrl`, `retrievedAt`, статус проверки. Государственные API: `verified`, `by: official_api`. Скрейпинг: `unverified` до проверки человеком, затем `verified`, `by: human`.
7. **Не выдумывать значения** (инвариант 6). Нет проверенного источника: `unverified` и задача человеку.
8. **Фикстуры и мок остаются** для тестов, стенда и локальной разработки.

## Шаг 2. База Supabase (1–1,5 недели)

Миграции через `supabase migration new`. Состав таблиц и правила RLS, ставок и версий — ADR-019.

| Таблица | Что хранит |
| --- | --- |
| `sources` | реестр источников: id, тип (`official_api`, `scrape`, `manual`), URL, расписание, статус |
| `dataset_versions` | версия набора **по домену** (`institutions`, `bank_metrics`, `products`, `treasury`, `reference`, `documents`): номер, `as_of`, `is_mock`, `current` |
| `institutions` | банки и кредитные союзы, `kind`, `partner_institution_ids`, сайт |
| `bank_metrics` | метрики по кварталам, значения рынка (медиана, среднее, перцентиль) |
| `products` | продукты, тиры в `jsonb`, ставки `numeric(11,8)` с check `0..1` |
| `documents`, `facts` | документы банков и факты с цитатой и страницей |
| `tax_tables`, `insurance_rules` | справочники, `jsonb` по году |
| `ads.sponsored_items` | реклама в отдельной схеме (ADR-006), не домен версии |
| `raw_snapshots` | сырые ответы: источник, URL, sha256, путь в Storage, время |
| `job_runs` | запуски: источник, начало, конец, статус, число записей, ошибки, байты и запросы по домену |
| `review_queue` | изменения на ручную проверку: что, было, стало, почему, решение |

- **Ставки наружу только через представления** с `apy::text`. Тест: каждая ставка из базы проходит `Rate` без потерь.
- **Центы** — `bigint` в диапазоне безопасного целого.
- **Версии по доменам.** Treasury обновляется каждый день, метрики раз в квартал. Публикация домена — одна транзакция с переключением `current`.
- **RLS:** анонимный ключ только читает опубликованные данные; запись только по ключу `service_role` из `ingest`.
- **Storage:** бакеты `raw/` (приватный) и `documents/` (PDF). Сайт отдаёт PDF через `/documents/[id].pdf`, CSP не меняется (ADR-018).
- **Регион `us-west-1`**, тариф Pro (ежедневные бэкапы; проект не засыпает). Функции Vercel заявлены в `iad1`. С этой машины `x-vercel-id` начинается с `fra1` — это точка присутствия запроса, не регион функций. Настройки проекта в этот день не открывались.
- **Версии домена** храним 30 дней. Откат: `pnpm db:rollback <domain> <version>` переключает `current`.
- **Сырые снимки** (рабочее правило, утвердить до шага 8): снимок, на который ссылается живая версия, хранится вместе с ней; остальные 90 дней.

**Начальная загрузка:** `pnpm db:seed --target local|staging` из фикстур (генерация, проверка схемами, одна транзакция, `--dry-run`, `--confirm prod`). Это рабочая база до появления реальных данных.

## Шаг 3. `gateway.supabase.ts` и переключение источника (1 неделя)

- `NEXT_PUBLIC_DATA_SOURCE=mock|http|supabase`, реализация загружается лениво (ADR-016 D2, правило `gateway-impl-dynamic-only`).
- `import 'server-only'`, ключи без `NEXT_PUBLIC_`.
- Маппинг строк, пагинация `PageOf`, ошибки в `GatewayError`:
  - нет записи — `not_found`;
  - сеть или 5xx — `unavailable`, `retryable: true`;
  - строка не прошла схему — `validation_failed`.
- `getDatasetInfo()` отдаёт `domains`. Верхние `asOf` и `isMock` остаются. Баннер DEMO DATA смотрит на домены страницы: он остаётся, пока среди них есть `isMock: true`. Свежесть реального факта считается от часов, свежесть мок-факта — от `asOf` его домена (ADR-019). Иначе при смеси доменов реальные ставки стареют от даты моков.
- **Обновление кеша страниц:** `cacheLife` по таблице `s-maxage` (спека §4) и `cacheTag` по домену. Домен `reference` один; налог кешируется на 604800 с, страхование на 86400 с. `POST /api/revalidate` с секретом вызывает `revalidateTag` после публикации. Сигнатуру `revalidateTag` в Next 16.4 сверить по `node_modules/next/dist/docs/`.
- **Тестовый набор контракта** против локального Supabase (`supabase start` в CI): задача на PR с меткой `db` и ночной прогон.
- e2e против `staging`: AC-3, AC-4 (ни одного запроса браузера к `*.supabase.co`), AC-5.

## Шаг 4. Ядро конвейера сбора (1 неделя)

Интерфейс источника, шаги конвейера, очередь проверки и уведомления — ADR-020.

Кратко: сырой ответ с sha256; чистый `parse` на снимках; схемы и пороги (APY 0–15%, срок > 0, взнос ≥ 0, сдвиг ставки > 50 б.п., пустой или вдвое меньший результат). Чистое публикуется. Подозрительный скрейп публикует только чистые строки, остальное в `review_queue`. Остальные домены при подозрении не публикуются. Ошибка оставляет прошлую версию.

Ручная проверка: `pnpm ingest:review`, `pnpm ingest:approve <id>`, `pnpm ingest:reject <id> --reason`. Issue на партию открывается в отдельном приватном репозитории. Этот репозиторий публичный, задач проверки в нём нет. Админ-страницы нет. Кто разбирает очередь (контроль — задачи старше 3 дней) — назначить до шага 4.

Пороги, принятые как рабочие 2026-11-04, можно поправить до шага 4: APY от 0 до 15%; сдвиг больше 50 б.п. на ручную проверку; пустой или вдвое меньший результат блокирует публикацию; у скрейпинга чистые продукты публикуются, подозрительные ждут.

IP раннеров GitHub банки часто режут. Ротацию прокси не используем. До шага 8 выбрать одно: такой банк уходит в ручной режим, либо скрейпинг идёт с отдельного worker со статическим IP.

Уведомления: падение задачи GitHub Actions (письмо) и суточная сводка (что обновлено, что в очереди, какие источники старше `STALE_AFTER_DAYS`).

## Шаг 8. Скрейпинг ставок банков (4–5 недель)

Правила 8.1–8.4 обязательны в коде (ADR-020). Здесь — порядок работ.

### 8.1 Правила

Только публичные страницы. `robots.txt` перед доменом. Не больше одного запроса раз в 5–10 с на домен, ночное окно, условные запросы. User-Agent с названием проекта, URL и техническим ящиком. Капча или блокировка — остановка, без обхода. Журнал запросов и байт. Исключение банка за 24 часа. Факты и короткие цитаты; снимки только во внутреннем хранилище.

### 8.2 Реестр банков

Список берётся из FDIC `institutions` (адрес сайта уже там) и NCUA. Очередь пилота: 10 онлайн-банков с высокими ставками, затем 50 крупнейших по депозитам, затем кредитные союзы с открытым членством. Имена банков в план не вписываем: их даёт FDIC на шаге 8. Если у банка есть публичный API ставок или страница для разработчиков с регистрацией по email, он вместо скрейпинга.

### 8.3 Адаптер

Порядок: JSON на странице, селекторы из конфига, Playwright только если без JavaScript ставок не видно. Нормализация в `Product` (`Rate` через `rateFromPercent`, взнос в центах). Допуск (резидентство, штат, минимум) человек вносит при первом подключении. Тест на сохранённом снимке. Поломка не публикует ничего.

### 8.4 Документы банков

PDF по ссылкам со страниц продуктов, хеш, бакет `documents`. Текст через pdf.js. Факты — предложение скрипта, подтверждение человека. Подсветка по символам цитаты (ADR-018).

| 1 | правила 8.1 в коде, реестр, каркас адаптера, 3 банка |
| 2 | 10 банков, очередь проверки, публикация в `staging` |
| 3 | документы банков, факты, подсветка по символам |
| 4 | 30–50 банков, мониторинг поломок адаптеров |
| 5 | замер: время поддержки на банк в неделю, доля поломок, доля ручных проверок; решение — расширять скрейпинг или искать поставщика данных для части банков |

## Шаг 9. Переключение сайта (0,5 недели)

- `NEXT_PUBLIC_DATA_SOURCE=supabase` в `staging`, затем в `prod`.
- `isMock: false` только для доменов с реальными данными. Баннер DEMO DATA снимается, только когда все домены на странице реальные.
- `/methodology`: реальные источники, частота обновления, метод расчёта рынка.
- Свежесть: реальные `retrievedAt`, пороги `STALE_AFTER_DAYS` (7 / 90 / `asOf` + 120) проверить на реальных данных.
- `DEMO_PASSWORD` остаётся до юридического «да» на публичный запуск.
- **Публичный запуск** (отдельное решение): убрать `noindex` и `disallow: /`, добавить `sitemap`, снять `DEMO_PASSWORD`.

## Шаг 10. Качество (сквозь все шаги)

- Тестовый набор контракта против Supabase (`staging`) — ночной прогон.
- Проверки качества данных ежедневно: доля устаревших записей по доменам, банки без продуктов, продукты без документа, незакрытые задачи в `review_queue` старше 3 дней.
- Lighthouse CI: бюджет и производительность не должны измениться (чтение только на сервере).
- e2e AC-4: ни одного запроса браузера к Supabase или к источникам данных.
